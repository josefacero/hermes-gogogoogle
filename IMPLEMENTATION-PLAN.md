# Remote delegation and MCP implementation plan

Base: `0d997e92ae741b2236a80a3ce4eac1d38455e9d9` on `master`. Existing local Hermes behaviour and tool names remain the compatibility baseline.

1. Extract delegation, worker execution, verification, Git inspection, jobs, and stats behind a shared API. Preserve Hermes' approval hook, configuration, output fields, profile context and existing tests. Keep the standard-library-only Hermes install.
2. Define a versioned, bounded JSON protocol for a fixed remote runner. The runner must enforce worker-owned workspace roots, resolve paths on the worker, run Git, AGY and verification there, and keep credentials out of output. SSH must authenticate using existing keys or agent, enforce host-key checking, never interpolate task or workdir into a shell command, and clean up timed-out or cancelled processes. Treat symlink races and process-tree cleanup as security review items, not solved by `resolve()` alone.
3. Route local and remote calls through the shared API. Keep approval meaningful: display worker, host, role, full task, workspace, verification and permission-skipping; fail closed for new interfaces unless the operator explicitly trusts the configured policy. Test policy tampering, invalid paths, SSH failures, timeouts, malformed responses, and remote Git/verification location.
4. Add an optional stdio MCP adapter with delegate, job and stats tools. Test with an actual supported client as well as fakes. State how the operator controls approval and avoid claiming MCP confirmation is equivalent to Hermes approval.
5. Add a non-root Docker Compose mock example, persistent state guidance and deployment documentation. Exercise Linux and macOS workers, container restart and cancellation before claiming those environments work. Keep account policy disclosures.
6. Run baseline and added tests, `hermes plugins validate .`, disposable-workspace integration and independent security/drift review. Prepare a feature-branch PR; do not merge or change the catalog or release without the required evidence and authorization.

Known acceptance dependencies: access to a real NAS-to-Mac worker pair and Docker are needed to verify those deployments. Existing background jobs are in-process daemon threads and explicitly become UNKNOWN after restart; restart recovery needs a deliberate design and tests.

Independent security review: the current `delegate()` bypasses the Hermes approval hook if invoked directly, and defaults to privileged `do`; MCP must not forward to it without an independent fail-closed policy. A disconnected SSH client does not prove that remote descendants stopped. Treat ambiguous completion as UNKNOWN, do not retry automatically, and require a worker-side deadline and process-group cleanup. A workspace allowlist is not a sandbox; use a restricted worker account, restrict the SSH key/command, disable forwarding, and default browser access off on new paths. Worker policy and allowed hosts must be operator-controlled rather than supplied by the caller. Remote changes remain on the worker unless explicitly synchronized. Isolate job results by OS user and validate response size and schema.

## Prototype status

The SSH transport, relay, inbox, supervisor and runner (`remote_*.py` and their tests) are an experiment for one case: a Windows lead and a Windows worker, review only. They are wired to Hermes (`antigravity_remote_review`, only when the operator configures a worker) and to the MCP `prepare` tool (`worker`). Still missing: a protocol version, worker identity, a full response schema, and filesystem checks that eliminate races. No Linux, macOS or Docker worker has been tested. The README section "Remote review on a second Windows machine" lists what was run.

`gogogoogle_mcp.py` is an experimental preview for Claude Code and Codex, tested on Windows only; the README section "Use from Claude Code or Codex" lists what was run. It requires configured roots and a separate `do` opt-in, but a trusted client can both prepare and execute without human review; it does not provide interactive human approval, and the roots are not containment. The orchestration body has been extracted to `delegation_core.py` using injected services; jobs, stats and execution services are not yet fully separated. It ships in the plugin as an experimental preview, not a supported interface.

Windows worker experiment (2026-11-11): `remote_supervisor.py` adds a worker-owned deadline (150 seconds, 480 with the verifier pass), a Windows Job Object with explicit termination, an output limit and a worker task policy (exact text by default). `remote_relay.py` and `remote_inbox.py` move the agy run into the signed-in desktop session, because on the tested machine agy could not use its sign-in (kept in Credential Manager) from a key-authenticated Windows SSH session; requests carry a random id and one inbox owns the spool at a time. Four earlier real review-only runs passed through Hermes and MCP, one per path with and without the verifier. After the final code fixes, one more verifier-on review passed through each path. This is an experiment, not a supported interface: the points above about protocol version, identity and races still stand, and a job object is cleanup, not containment.
